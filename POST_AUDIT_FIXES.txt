FIX 1 - CHECKPOINT AND RESUME MUST NOT CHANGE THE COMPUTATION GRAPH
         (Codex DML-A01, HIGH; part of DML-A05)
==============================================================================

1. What Codex found
   A checkpoint could be loaded into a model with a different recurrence
   schedule whenever tensor names and shapes matched.  Codex's probe B
   saved a depth-2 "cycle" model and loaded it into a depth-3 "sequence"
   model: accepted, logits changed by 0.177509.  The trainer built the
   model from the command-line config and never compared it with the
   checkpoint's.  A missing resume checkpoint fell back to step 0, and an
   explicit experiment directory bypassed ID allocation even for a fresh
   run, so mixed histories could be written into an existing experiment
   such as DML-0001.  (DML-A05, same area: both loaders tolerated a
   missing lm_head.weight even for untied models.)

2. How the defect was reproduced (post_audit/repro_before.txt)
   - Codex's probe, re-run: depth-2 cycle checkpoint loaded into depth-3
     sequence: "ACCEPTED; logit delta 0.17750859260559082".
   - New case: the same recurrent checkpoint loaded into a plain
     2-block baseline (identical tensor layout): "ACCEPTED; delta
     0.20899996161460876".  A recurrent model's weights were silently run
     as a conventional Transformer.
   - By inspection of trainer.py: `if resume and ... latest() is not None:
     load ... elif resume: print(WARNING ... starts from step 0)`; and of
     scripts/train.py: `finally: ... set_status(exp_dir, status)` runs for
     ANY exception.

3. Why the problem occurred
   The checkpoint format described weights (safetensors names/shapes) and
   stored the config, but nothing compared the stored config with the
   model receiving the weights.  Weight sharing makes this a real hazard:
   n_layers counts STORED blocks, so every recurrence depth and order of a
   2-block model, and the 2-block baseline, share one state_dict layout.
   Shape checks cannot distinguish computation graphs that differ only in
   how stored blocks are wired.

FIX 2 - STRICT KV-CACHE VALIDATION   (Codex DML-A02, MEDIUM)
==============================================================================

1. What Codex found
   A heterogeneous cache used slot 0 for positions and accepted other
   slots with different histories.  Shortening slot 1 from 5 to 2 changed
   logits by 0.00435843 (FP64) with no exception.  An empty cache raised
   IndexError before the length check.  Same-shaped slots carry no
   provenance.

2. How the defect was reproduced (post_audit/repro_before.txt, FP32,
   smoke-size depth-2 recurrent model)
   - slot 1 shortened to 2 positions: ACCEPTED, delta 0.0561
   - slot 2 replaced by None (found here, not in the Codex report):
     ACCEPTED, delta 0.1187.  That application attended to the new tokens
     only.
   - empty list: IndexError
   - wrong head count, wrong batch, float64 slot, k/v length mismatch,
     input batch != cache batch: RuntimeError from deep inside attention,
     no indication which slot or why.
   - Provenance gap, by construction: a depth-2 "cycle" cache [0,1,0,1]
     and a depth-2 "sequence" cache [0,0,1,1] have identical shapes.

3. Why the problem occurred
   forward() derived the positional offset from caches[0][0].size(2) and
   then handed each slot to its block without checking it.  Inside
   attention a shorter slot is not an error: keys are concatenated and the
   mask is built from that slot's own length, so the application silently
   attends to a different history while positions follow slot 0.  With
   recurrence there are A slots instead of n_layers, which widens the gap.

FIX 3 - INFERENCE PROFILING   (Codex DML-A03, HIGH)
==============================================================================

1. What Codex found
   (a) Analytic weight/KV bytes assumed 2-byte storage while checkpoints
       load in FP32.
   (b) Each generate() reset the CUDA peak, so the aggregate reported only
       the last run's peak.
   (c) Context strings undershoot their targets: a word tokenizer gave 9
       tokens for both 16 and 32.
   (d) Exact-full prompts leave zero decode tokens.
   (e) TTFT read perf_counter after launching CUDA prefill, before the
       device finished.
   (f) Prefill K/V are views of the fused QKV output and retain Q storage:
       43,200 underlying bytes for 28,800 logical bytes.  Decode
       concatenation keeps the old cache live.
   The review also asked for profiling that cannot pair a model with the
   wrong configuration, device-wide memory, and results that state dtype,
   lengths and depth.

2. How the defect was reproduced (post_audit/repro_before.txt)
   (a) accounting weight_bytes 216,064 vs actual FP32 parameter bytes
       432,128 for the smoke-size model: a factor of 2.
   (c) sweep with Codex's word tokenizer: [(16, 9), (32, 9)].
   (d) byte tokenizer, target = context_length 128: actual 128 prompt
       tokens, decode_tok_per_s None.
   (f) prefill cache: logical 10,240 bytes, retained storage 15,360 bytes.
   (b), (e) and profile_model's cfg/model pairing were confirmed by
   reading the code.  They cannot be observed on a CPU-only build.

3. Why the problem occurred
   The profiler was written for the conventional baseline, where cfg and
   model always agreed.  It assumed bf16 storage in its formulas, used text
   prompts for convenience, and inherited generate()'s per-call peak reset
   and CPU-style timing.

BEHAVIOUR AND DEFINITION CHANGES (do not compare old and new numbers blindly)
==============================================================================
  - generate(): ttft_s now = synchronized prefill + first-token sampling
    (was: unsynchronized prefill forward only), and is None when no token
    can be sampled.  New field prefill_s.  prefill_tok_per_s now divides by
    prefill_s.  No profile.json from before this change exists in the
    repository, so no historical number is affected.
  - profile_context_sweep(): targets are exact token counts and are capped
    at context_length - max_new_tokens; rows gained fields.
  - profile_inference(): peak VRAM = max over all timed runs (was: last
    run only).
  - profile_model(): raises ValueError when cfg does not describe the
    model; analytic byte estimates are in the model's real dtype (FP32 => 4
    bytes, previously always 2).
  - scripts/train.py: --experiment-dir requires --resume.  A refused resume
    exits 1 and leaves the experiment's status untouched.
  - Trainer: resume refuses ANY model-section change (dropout included),
    refuses a missing checkpoint (was a warning and a silent restart from
    step 0), and refuses a fresh run into a directory with checkpoints.
  - load_checkpoint / build_model_from_checkpoint: refuse architecture or
    schedule mismatches and untied checkpoints without lm_head.weight.
  - forward(): malformed caches raise CacheValidationError (a ValueError);
    returned caches are ApplicationCache (a list subclass).
  - pyproject.toml: torch>=2.4.
  - [re-review] Result fields "dtype" -> "weight_dtype" + "kv_dtype"
    (+ "autocast" in profile_model).  KV estimates use the KV dtype.
  - [re-review] A fresh run refuses directories with ANY checkpoint trace.
    A resume refuses a missing/stale index, changed data provenance and a
    held writer lock.  A crashed-swap .bak is recovered only after
    validation.  Checkpoints gain a "data_provenance" record.
  - [round 3] Trainer() itself takes the writer lock (was: train()), and
    raises if another writer holds it.  train() gained release_lock;
    Trainer gained close()/release_lock().  A crashed-swap .bak is loaded
    in place and renamed only after a successful load.  Provenance gains
    train_bin_sha256/val_bin_sha256, and token counts now come from the
    files.  A packed file whose size disagrees with meta.json is refused.
  - [round 4] A Ctrl+C inside an optimizer update writes no rescue
    checkpoint.  A non-finite loss, gradient norm or validation loss ends
    the run as FAILED (summary "failure") without a checkpoint.  The final
    evaluation now precedes the final checkpoint.  Resume refuses changed
    trajectory fields (a changed training.steps used to be a warning).
    --extend-steps / extend_steps=True is the only way to lengthen a run
    and is recorded in "protocol_deviations".  Metric rows gain "attempt";
    experiments gain sessions.jsonl.  Summaries gain failure, attempt,
    protocol_deviations and recovery_checkpoint, and tokens_trained is the
    committed count.
