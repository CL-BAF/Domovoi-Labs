# Proposed human approval and ledger protection

The repository owner must choose a named approving GitHub account or a small named team and verify its membership. This proposal leaves GitHub settings and the ledger untouched. Repository write access alone does not grant scientific approval under the proposed policy. The automation identity may submit verified state transitions under an approved plan. The named human decides whether the plan, criteria and expenditure are authorized.

## Owner actions before the first approval

1. In both repositories, open **Settings → Rules → Rulesets** (or the corresponding protected-branch setting). In Research, target `research/real-data-calibration` precisely. In Labs, target the selected implementation integration ref and any release branch used for freeze. Disable deletion and force pushes, require linear history, and use required checks and signed commits where supported by the repo and clients. Test behavior on a disposable ref before applying the final rules. [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
2. On the respective protected bases, add `.github/CODEOWNERS` after selecting the approver. In Research it should cover itself, `/experiments/protocol/`, and `/docs/EXPERIMENT_PROTOCOL.md`. In Labs cover itself, `/scripts/experiment_protocol.py`, `/domovoi/experiments/`, `/research_workloads/` and any frozen instrument code. Require code-owner approval, dismiss stale approvals, and bind approval to the final reviewed push. Ensure the chosen owner or visible team has the GitHub access required for CODEOWNERS. [GitHub code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)
3. Have the approver review the exact plan commit, implementation SHA, primary endpoints, hashes and resource cap. Record their verified approval and plan SHA in a durable GitHub review or signed attestation, then advance the canonical row under the protected workflow. Approve changes in a new reviewed plan. Store artifact hashes, terminal proof, and the analysis revision in append-only history.
4. The current launcher uses direct fast-forward machine pushes for RUNNING and terminal states. Requiring PRs on every update would block that code. Before deployment, use a dedicated, tightly scoped service identity for machine writes and implement an independently reviewed transition check. Validate that only the trusted human workflow can publish APPROVED and that the machine can publish only a legal claim or terminal diff against its exact approved parent. If using a ruleset bypass, scope it to the dedicated identity and the smallest possible ruleset while retaining force-push/deletion protection separately. A bypass by itself cannot enforce per-file or per-transition authority. Where this cannot be enforced with available GitHub settings, use a mediated writer that validates identity, signatures, paths and transitions, or change the launcher workflow before use.
5. Restrict credentials to the service and owners, retain repositories' audit history, and periodically verify the canonical ref and published artifact hashes from an independent checkout. Handle exceptional recovery via an owner-reviewed terminal correction backed by receipt and evidence. A credentialed actor who can publish a forged claim and choose its initial completion commitment can fabricate history without these controls.

The current launcher verifies commit contents, ordering and completion evidence format. GitHub review identity, cryptographic attestation from a runner, protected settings, and service enforcement still require deployment and verification by the owner.
