A.1 Starting point
------------------
The local project folder was empty.  The project owner pointed to the
previous generation at https://github.com/CL-BAF/Domovoi-Labs (branch main,
downloaded as a ZIP because git is not installed on this machine).  The
owner's rule for this generation: do not reuse anything from previous
generations unless it improves the overall design.

Decision: the previous generation's pipeline was kept as the base, unchanged
except where noted below.  Reason: the brief requires that the existing
baseline Transformer stays the experimental control, that DML-0001 is not
disturbed, that existing configs and checkpoints keep loading, and that the
existing tests keep passing.  A rewritten pipeline would make the new model
incomparable with DML-0001 (different data loader, optimiser grouping,
scheduler, evaluation code...).  Keeping the pipeline is therefore the
design choice that makes the A/B comparison valid.  It passes the "only if
it improves the design" test because an A/B experiment is only meaningful
when everything except the architecture is held fixed.

Environment created for this work (machine changes, all user-scope):
  - Python 3.13.17 installed with `winget install Python.Python.3.13` (there
    was no Python on the machine; the owner approved this).
  - A virtual environment at .venv/ (already git-ignored by the project)

A.2 What was implemented
------------------------
1. A new model, DomovoiRecurrentTransformer, registered as
   "domovoi_recurrent_v1".  It stores n_layers distinct Transformer blocks
   and applies them recurrence_depth times each (effective depth
   A = n_layers * recurrence_depth).  Two reuse orders: "cycle"
   (0,1,2,0,1,2,...) and "sequence" (0,0,1,1,2,2,...).
2. A one-method hook in the baseline (application_schedule) that says which
   stored block runs at each depth position.  The baseline returns
   [0, 1, ..., n_layers-1], so its behaviour is unchanged (verified
   bit-exactly against the original file, see B.3).
3. Two new config keys (model.recurrence_depth, model.recurrence_order)
   with defaults that mean "no recurrence", so every old config and
   checkpoint loads unchanged.  Architecture validation now reads the model
   registry instead of a hard-coded string.
4. Profiling: parameter USES per token ("applied" parameters) and effective
   depth, plus a closed-form accounting module (FLOPs, KV-cache bytes,
   weight bytes) that is clearly labelled as an estimate.
5. Metadata/report plumbing so experiment records show the recurrence
   settings.
6. Two CPU-only scripts: inspect_model.py (build a model, print counts, run
   an offline cached-vs-uncached smoke test) and
   plan_recurrent_experiments.py (the controlled experiment matrix).
7. 63 new automated tests (tests/test_recurrent.py).
8. Documentation: this file and docs/RECURRENT_ARCHITECTURE_RESEARCH.md.

A.5 How the architecture functions
----------------------------------
Input token ids -> token embedding + learned absolute position embedding ->
residual stream x (shape B x T x d_model).

Then, for every entry b in the application schedule (length
A = n_layers * recurrence_depth):
      x <- Block_b(x)        where Block_b is pre-LayerNorm:
                             x = x + Attn_b(LN1_b(x));  x = x + MLP_b(LN2_b(x))
The SAME Python module object (and therefore the same weight tensors) is
used every time b repeats.

Then final LayerNorm -> output projection (tied to the token embedding) ->
logits -> softmax / cross-entropy.

The "recurrent working state" is simply the residual stream x as it passes
from one application to the next.  Nothing is detached: gradients flow
through all A applications, and a shared weight's gradient is the sum of the
gradients from every application that used it (verified by a test that
compares against an explicitly unrolled copy of the network).

KV cache: in autoregressive decoding every application caches its own keys
and values, because the input x to the k-th application of a block differs
from the input to its j-th application.  The cache therefore has A entries,
not n_layers.  Weight sharing does NOT share the KV cache.

A.6 How it differs from the original Transformer
------------------------------------------------
Identical: block design, attention, MLP, LayerNorm, GELU, biases, learned
positions, tied embeddings, loss, KV-cache mechanics, checkpoint format,
generation, training loop.
Different:
  - number of stored blocks (n_layers) is decoupled from depth (A);
  - residual-projection init std uses A instead of n_layers;
  - parameter bookkeeping distinguishes unique (stored) parameters from
    applied (used-per-token) parameters.
With recurrence_depth = 1 the recurrent model IS the baseline: same
parameter names, same initial weights for the same seed, bit-identical
logits (tested).

A.7 Inspirations (see docs/RECURRENT_ARCHITECTURE_RESEARCH.md section 3 for
full, verified citations)
-------------------------------------------------------------------------
  Universal Transformers (Dehghani et al., arXiv:1807.03819) - recurrence
    over depth with shared weights.
  Recurrent stacking of layers (Dabre & Fujita, arXiv:1807.05353).
  ALBERT cross-layer sharing (Lan et al., arXiv:1909.11942).
  Takase & Kiyono, "Lessons on Parameter Sharing across Layers in
    Transformers" (arXiv:2104.06022) - the CYCLE / SEQUENCE assignment
    names used for recurrence_order.
  Geiping et al. recurrent-depth LM (arXiv:2502.05171); Saunshi et al.
    looped transformers (arXiv:2502.17416); Bae et al. Relaxed Recursive
    Transformers (arXiv:2410.20672) and Mixture-of-Recursions
    (arXiv:2507.10524) - modern evidence and the per-recursion KV issue.

A.8 What is genuinely experimental
----------------------------------
Whether reusing blocks gives more capability per GiB of MEASURED inference
memory than spending the same memory on a conventional Transformer.  This
has NOT been tested.  No model has been trained.  Everything about quality
is unknown.

A.9 Limitations that remain (details in Part E)
-----------------------------------------------
  - No training, no evaluation, no GPU measurement was performed.
  - KV cache and per-token compute grow with effective depth.  At 8K context
    the KV cache dominates memory for all planned sizes (derived table in
    Part C.9), which directly threatens the hypothesis.
  - The control (and therefore v1) uses learned absolute positions limited
    to the configured context (512 in baseline_small): 8K context is not yet
    supported by either model without a larger position table.
  - The default dataset (tinyshakespeare) is too small for a valid
    comparison: fewer-parameter arms may win through regularisation alone.
  - No git on this machine, so new runs would record no commit hash
    (RESEARCH.md requires one).

A.10 Post-audit remediation (Codex audit: APPROVE AFTER FIXES)
--------------------------------------------------------------

(post_audit/repro_before.txt), then fixed and covered by regression tests
(tests/test_post_audit.py, 69 tests).  Details: POST_AUDIT_FIXES.txt.

                   including the application schedule.  Every load verifies
                   it before touching weights.  Resume requires the same
                   complete model section, refuses missing checkpoints and
                   refuses fresh runs into existing experiments.  A refused
                   resume no longer rewrites the experiment's status.

                   model and schedule), shapes, batch, heads, equal prefix
                   in every slot, device, dtype and context bound.
  Fix 3 (DML-A03)  Profiling: estimates in the model's real dtype and
                   labelled; exact prompt lengths; decode headroom; one peak
                   over all timed runs; CUDA-synchronised timing; cfg/model
                   signature check; exact KV byte counts.  NOT verified on
                   CUDA.
  Fix 4 (DML-A04)  Planner: no inherited experiment IDs, no silent
                   overwrite, per-seed configs, --pilot.
  Fix 5 (DML-A08)  recurrence_schedule rejects bool/non-int.
  Also (DML-A05)   An untied model no longer accepts a checkpoint without
                   lm_head.weight.

PART C - MATHEMATICAL EXPLANATION
==============================================================================

C.1 Symbols
-----------
  V        vocabulary size                      (4096 in baseline_small)
  d        model width, d_model                 (640)
  h        attention heads; d_h = d / h          (10; 64)
  f        MLP hidden width, ffn_dim            (1728)
  N        stored (distinct) blocks, n_layers
  r        recurrence_depth
  A        effective depth = N * r  (block applications per forward)
  T        sequence length of the current input
  L        number of keys a query attends to (<= context length)
  C        context_length (size of the learned position table)
  w_t      token id at position t
  x^(a)_t  residual-stream vector (in R^d) at position t after application a
  sigma(a) stored-block index used by application a  (a = 1..A)
  theta_b  parameters of stored block b  (b = 1..N)
  E        token embedding matrix, V x d;  P  position table, C x d

DERIVED vs SPECULATIVE: everything in C.1-C.9 is a mathematical property of
the implementation.  Statements about capability are speculative unless
labelled otherwise, and are collected in Part D/E.

C.2 Embedding
-------------
  x^(0)_t = E[w_t] + P[t]                (t counted from the start of the
                                           sequence, continuing after any cache)
Identical to the baseline.

C.3 Attention inside one application (block b, input X in R^{T x d})
---------------------------------------------------------------------
  LN(z) = gamma * (z - mean(z)) / sqrt(var(z) + eps) + beta   (per vector)
  [Q K V] = LN1_b(X) W^qkv_b + b^qkv_b          W^qkv_b in R^{d x 3d}
  per head i:  H_i = softmax( Q_i K_i^T / sqrt(d_h) + M ) V_i
  M_{s,t} = 0 if t <= s (plus cache offset), -inf otherwise     (causal mask)
  Attn_b(X) = [H_1 ... H_h] W^o_b + b^o_b
The mask makes the output at position s a function only of positions
<= s, at every application.  A composition of causal maps is causal, so
the stacked A applications remain causal (tested).

C.4 Feed-forward
----------------
  MLP_b(Y) = GELU( LN2_b(Y) W^1_b + b^1_b ) W^2_b + b^2_b,
  W^1_b in R^{d x f}, W^2_b in R^{f x d}.

C.5 Recurrent hidden-state update
---------------------------------
One application of stored block b is the map
  F_b(X) = Y + MLP_b(Y),   with  Y = X + Attn_b(X)      (pre-LN residual)
The model applies
  x^(a) = F_{sigma(a)}( x^(a-1) ),     a = 1, ..., A
with
  baseline :  sigma(a) = a,                     A = N
  cycle    :  sigma(a) = ((a - 1) mod N) + 1      -> 1..N, 1..N, ...
  sequence :  sigma(a) = ceil(a / r)              -> 1,1,..,2,2,..
For N = 1 the model iterates one fixed map F_1 A times, which makes it a
discrete dynamical system over depth: x^(a) = F_1^a(x^(0)).  The "working
state" carried between iterations is the full residual stream x^(a) (all
positions); no other state exists.

C.6 Parameter reuse and gradient propagation
--------------------------------------------
Write theta^(a) for "the parameters used by application a".  Sharing
imposes the constraint theta^(a) = theta_{sigma(a)}.  The chain rule over
the unrolled graph gives
  dLoss/dtheta_b = SUM over {a : sigma(a) = b} of  dLoss/dtheta^(a)
i.e. the gradient of a shared tensor is the sum of the gradients it would
receive if every application had its own copy.  This is the same identity as
backpropagation through time in an RNN, here unrolled over DEPTH rather than
time.  PyTorch implements it automatically because the same Parameter
object appears several times in the graph (verified numerically by
test_shared_equals_unrolled_copies).
State gradients:
  dLoss/dx^(a-1) = dLoss/dx^(a) * J_a,
  J_a = dF_{sigma(a)}/dx = I + d(residual branches)/dx.
The identity term I (from the residual connections) gives every
application a direct gradient path to the loss, which mitigates vanishing
gradients across depth.  Nothing is detached, so the gradient through all A
applications is exact (no truncation).
Consequence: shared parameters receive about r times as many gradient
contributions as an unshared layer's parameters.  Their gradient magnitudes
and effective learning rate therefore differ from the baseline's, and the
shared LR and gradient clipping act on a differently scaled gradient.  This
is a potential optimisation difference to watch, not a known problem.

C.7 Output probabilities
------------------------
  p( w_{t+1} = v | w_<=t ) = softmax( LN_f( x^(A)_t ) E^T )_v      (tied head)
  Loss = mean over the batch and positions of  -log p(target)
Identical to the baseline; only the computation of x^(A) differs.

C.8 Computational complexity (per token, forward; see accounting.py)
--------------------------------------------------------------------
  block parameters        p_b   = 4d^2 + 2df + 9d + f
  unique (stored) params  P_u   = Vd + Cd + N p_b + 2d   (+ Vd if untied)
  applied params          P_app = P_u + (A - N) p_b
  forward FLOPs/token     ~ A (8d^2 + 4df + 4dL) + 2Vd
  training FLOPs/token    ~ 3 x forward
  sequence of length T    matmuls O(A T d (d + f)), attention O(A T^2 d)

  Comparison with a conventional Transformer of depth N_conv:
                         conventional (N_conv)   shared-core (N stored, r)
    stored params        ~ N_conv p_b             ~ N p_b
    FLOPs / token        ~ N_conv (...)           ~ N r (...) = A (...)
    KV cache             ~ N_conv                 ~ A
  => With equal A, FLOPs and KV cache are EQUAL and stored weights are r
     times smaller.  With equal N, stored weights are equal and FLOPs and KV
     cache are r times LARGER.
  baseline_small numbers: p_b = 3,857,728.  2 stored blocks at depth 4 store
  10.67M parameters but apply 33.81M per token, the same compute as an
  8-layer model of 33.81M stored parameters.

C.9 Memory complexity
---------------------
  Weights:         P_u x bytes                             ~ N
  KV cache:        2 x A x d x L x bytes  (batch 1)       ~ A L
  Inference activations: one application at a time       ~ T (d + f) (+T^2 h
                   if the attention kernel materialises scores)
  Training activations stored for backprop: ~ A x B x T x (c1 d + c2 f)
                   (+ A B h T^2 without fused attention)  ~ A
  Gradients + AdamW state (fp32): ~ 3 x P_u x 4 bytes      ~ N
So sharing shrinks everything proportional to N (weights, gradients,
optimiser state, checkpoint), and leaves unchanged everything
proportional to A (activations, KV cache, FLOPs).

batch 1; produced with architecture_accounting; NOT measurements):

    DML-0001 (B10)     10         88.6        200.0        288.6
    B02                 2         29.7         40.0         69.7
    B04                 4         44.4         80.0        124.4

For every arm at this width the KV cache at 8K is larger than the weights.
R02x8 stores 4.5x fewer weight bytes than B16 but has the same 320 MiB KV

at risk at this size; the point is that the RELATIVE benefit of sharing
shrinks as context grows.  At larger widths the weights' share grows again
(weights ~ d^2 x N, KV ~ d x A x L), so this balance must be recomputed for
any scaled configuration.  Activation memory and allocator overhead are not
included; only a CUDA measurement can give the real peak.

PART D - DESIGN DECISIONS
==============================================================================

D.1 Subclass the baseline and add one hook (application_schedule)
  Why: both arms share one forward(), one attention implementation, one
    init routine.  Any difference must come from the schedule.
  Alternatives: (a) an independent module copying the baseline code;
    (b) a wrapper that calls baseline blocks from its own loop; (c) building
    the baseline with duplicated references to the same block object inside
    nn.ModuleList.
  Why not: (a) and (b) duplicate the context, cache, embedding and loss
    logic, where silent divergence could hide.  (c) would make
    state_dict/safetensors contain aliased keys and confuse the checkpoint
    deduplication code.
  Advantages: minimal code (128 lines); bit-exact equivalence at depth 1;
    checkpoint format unchanged.
  Disadvantages: the control file had to change (13 changed code lines plus
    comments, all listed in B.3; proved bit-identical).  Future architectures that need a different forward()
    will need their own module anyway.
  Validate: test_depth1_is_exactly_the_baseline; the original-vs-modified
    equivalence script (B.3).
  Abandon if: a future variant needs per-application state that a schedule
    cannot express (e.g. per-token adaptive depth).  Then write a dedicated
    forward instead of stretching the hook.

D.2 n_layers = number of STORED blocks; add recurrence_depth/order
  Why: config shape stays the same across architectures (registry
    convention); defaults preserve every old config and checkpoint.
  Alternatives: a new "n_unique_blocks" key with n_layers meaning effective
    depth; or a full explicit schedule list in YAML.
  Advantages: a depth-1 recurrent config is the baseline config plus a
    different architecture string.  Validation is simple.
  Disadvantages: "layers=2" in a report means 2 stored blocks, which can
    mislead; the report adds an explicit effective-depth line to counter
    this.  An explicit schedule list would be more general (e.g. CYCLE(REV)).
  Validate: config tests.  Abandon if: schedules beyond cycle/sequence are
    needed.  Then add an optional explicit schedule key.

D.3 Recurrent state = the residual stream only (no input re-injection, no
    iteration embedding, no persistent memory)
  Why: the brief asks to isolate the effect of sharing and depth and to
    avoid untested extras.  This is the minimal recurrent formulation.
  Alternatives: re-adding the embedding at each iteration (as in Geiping et
    al.); learned per-iteration embeddings or per-iteration LayerNorms so a
    block knows which pass it is on; a compact memory carried between
    tokens.
  Advantages: zero extra parameters; exact baseline equivalence at depth 1;
    one variable changed at a time.
  Disadvantages: a shared block cannot tell which iteration it is on, which
    may limit how differently it can behave in early and late passes.
    Possibly a real capacity handicap.
  Validate: F8 comparison plus per-iteration early-exit diagnostics.
  Abandon (move to an extension) if: early-exit loss stops improving after
    the first iteration, or the gap closure in F8 is < 0.25.

D.4 Residual init std = 0.02 / sqrt(2 x A) (effective depth)
  Why: the residual stream receives 2A additive updates per forward.  GPT-2-
    style scaling by the number of additive updates keeps the initial stream
    variance comparable to a conventional model of the same effective
    depth.  Compute-matched arms (equal A) therefore start from the same
    per-branch output scale.
  Alternative: scale by stored N (smaller divisor, so larger init and
    faster variance growth for deep recurrence).
  Disadvantage: smaller initial updates may slow early learning at large A.
  Validate: test_numerically_stable_at_depth_8 (init only); training curves
    over the first few hundred steps.  Ablation if needed: the same arm with
    the N-based scale.
  Abandon if: recurrent arms consistently learn slower early on and the
    N-scaled ablation fixes it.

D.5 One KV-cache entry per APPLICATION
  Why: correctness.  Application k of block b sees a different input than
    application j, so its K and V differ (tested).  Reusing them would change
    the function.
  Alternative: share K/V across recursions (an approximation discussed in
    Mixture-of-Recursions).  That is a different model that must be trained
    that way, not a cache optimisation.
  Advantage: cached == uncached exactly (atol 1e-5, 8 configurations).
  Disadvantage: KV memory proportional to A (C.9), the main threat to the
    hypothesis at 8K.
  Validate: cached-vs-uncached tests; measured context sweep on GPU.
  Abandon (switch to a KV-shared variant) if: S3 fails mainly because of KV
    memory.

D.6 Two reuse orders ("cycle", "sequence"), default cycle
  Why: the brief requires a configurable reuse structure.  Cycle is the
    common "looped" formulation (whole stack re-run); sequence is the
    simplest alternative from Takase & Kiyono.  Each costs one line.
  Alternatives: CYCLE(REV) (1,2,3,3,2,1); arbitrary user-supplied schedules;
    a single fixed order only.
  Advantages: lets ablation O test whether order matters at no complexity
    cost; the default matches most of the literature.
  Disadvantages: one more config knob, and one more arm to train.  Neither
    order lets a block know which pass it is on (D.3).
  Validate: ablation O (R02x4 vs R02x4s, at least 3 seeds each).
  Abandon (drop "sequence") if: the difference is within seed noise.  Keep
    cycle for simplicity.  If sequence is clearly better, make it the default
    and re-run C.

D.7 Full backpropagation through all applications (no truncation)
  Why: the brief forbids silent detaching; the exact gradient is the clean
    reference that any approximation must be compared against.
  Alternatives: truncated backprop through only the last k iterations, as in
    some recurrent-depth work (saves training activation memory); detaching
    early iterations entirely.
  Advantages: exact gradients; no extra hyperparameter (k); matches the
    baseline's optimisation exactly at depth 1.
  Disadvantages: training activation memory and backward compute
    proportional to A, which limits trainable depth on a 4 GiB GPU (gradient
    accumulation helps only with batch size, not with depth).
  Validate: gradient-flow tests (done); in real runs, check that training
    fits memory at A = 16 and that gradient norms stay bounded.
  Abandon (switch to truncation as a SEPARATE, documented experiment) if:
    deep arms cannot be trained within the memory budget even at batch 1 per
    micro-step, or if gradient norms explode with A despite clipping.

D.8 Keep learned absolute positions (same as the control)
  Why: changing the positional scheme (e.g. to RoPE) in only one arm would
    confound the A/B comparison; changing it in both would change the
    control and invalidate DML-0001 as M1 reference.
  Alternatives: rotary (RoPE) or ALiBi positions in both arms; NoPE.
  Advantages: zero confounds at 512 context; exact baseline equivalence;
    DML-0001 remains the valid control.
  Disadvantages: 8K context needs an 8192-row learned table (5.2M extra
    parameters at d=640) that has never been trained.  Learned tables do not
    extrapolate beyond their length.  This blocks the project's 8K
    requirement for BOTH models.
  Validate: none needed at 512.  Before any 8K experiment, a positional
    ablation on the BASELINE alone (learned vs RoPE at 512) is needed to show
    the new scheme is not worse, and then both arms switch together.
  Abandon (switch both arms to a relative scheme) when: the project moves
    to 8K experiments, which it must for qualification.  This decision is
    for the project owner.

D.9 Registry-driven architecture validation; the baseline refuses
    recurrence keys
  Why: one source of truth for valid names; a mislabelled experiment
    (baseline config with recurrence keys that would be silently ignored)
    becomes impossible.
  Alternatives: keep the hard-coded string check and extend it; per-
    architecture config sections; silently ignore irrelevant keys.
  Advantages: adding an architecture needs one registry line; integrity
    errors fail at config load, before any GPU time is spent.
  Disadvantages: config.py imports the model package (inside validate) and
    therefore torch, which every environment of this project has anyway.
    The check is architecture-specific (only the baseline is guarded), so
    future architectures must add their own rules.
  Validate: test_recurrent_config_invalid, test_baseline_rejects_recurrence_keys,
    test_pre_recurrence_configs_still_load (all pass).
  Abandon (move to per-architecture config sections) if: several
    architectures with disjoint options make the flat `model:` section
    unwieldy.

D.10 Experiment matrix: width fixed at d=640, power-of-two ladder,
     token-matched, one base config
  Why: equal width makes every arm differ ONLY in depth and sharing.  The
    power-of-two ladder gives exact compute-matched partners for r = 2/4/8
    and traces the conventional loss-vs-memory frontier the hypothesis must
    beat.
  Alternatives: width-matched-by-parameters designs (a wider shared model vs
    a narrower deep one; informative but change two variables at once);
    comparing only against DML-0001 (10 layers; no exact partners for
    r = 4, 8).
  Advantages: clean single-variable comparisons; both param-matched and
    compute-matched groups from one set of 10 runs; generated from code, so
    reproducible.
  Disadvantages: on tinyshakespeare the design is invalid for capability
    claims (about 80 epochs, so overfitting favours small models); a larger
    corpus requires authorisation.  Missing comparison: equal stored params
    AND equal training FLOPs (e.g. B02 trained 4x longer vs R02x4), which
    also needs a larger corpus.  The width is fixed at one size, so scale
    trends are unknown (E.7).
  Validate: before the matrix, run B08 with 3 seeds to measure seed noise.
    Check that the baseline ladder is monotone (B02 > B04 > B08 > B16 in
    loss).  If it is not, the corpus or budget cannot resolve depth
    effects at all.
  Abandon / redesign if: the baseline ladder is not monotone beyond noise,
    or train/val gaps show heavy overfitting.  Then the matrix cannot answer
    the question with this corpus/budget.

D.11 "Applied parameters" and closed-form accounting kept separate from
     measurements
  Why: parameter count alone is not a capability measure, and the brief
    forbids presenting estimates as measurements.  Distinct key names
    ("analytic_estimates", "est_*", "measured_parameter_counts") prevent
    mixing.
  Alternatives: report only stored parameters; estimate FLOPs with a
    profiler (torch.utils.flop_counter) instead of closed forms; estimate
    memory instead of measuring it.
  Advantages: experiments can be designed before any training; closed forms
    are exact for parameter counts (tested against real tensors) and
    transparent for FLOPs.
  Disadvantages: FLOP and KV formulas ignore small ops, allocator overhead
    and activations, so they are not a substitute for CUDA measurement.
  Validate: compare analytic KV/weight bytes against measured CUDA peak
    memory in the context sweep of the first authorised run.
  Abandon (replace with a measured FLOP counter) if: measured and analytic
    numbers disagree by more than about 10% for the dominant terms.

D.12 [POST-AUDIT] Checkpoint compatibility by explicit architecture
     signature (Fix 1)
  Decision: checkpoint.json stores a signature (architecture id, all
    structural dimensions, depth, order, explicit application schedule).
    Every loader compares it with the receiving model before loading.
    Resume additionally requires the complete model section to match.
  Alternatives considered: (a) compare only recurrence_depth/order: misses
    baseline-vs-recurrent with equal n_layers and code-level changes to a
    schedule's meaning; (b) encode the schedule in parameter names
    (e.g. one state_dict entry per application): breaks the "no
    copies / same names as the baseline" property and every existing
    checkpoint; (c) always rebuild from the checkpoint and ignore the
    caller's model: right for inference (already done), wrong for resume,
    where the run's config must be checked, not overridden.
  Pros: catches every same-shape graph change found; legacy checkpoints
    load through ModelSection defaults; messages name each differing
    field.  Cons: a strict rule.  Resuming with a deliberately changed
    dropout is now refused; that has to be a new experiment.
  Validating experiment: the regression tests (B.20); mutation M1 fails 7
    of them.
  Abandon if: a legitimate workflow needs cross-architecture weight
    transfer (e.g. initialising R02x4 from B02's blocks).  That should be
    an explicit "fork/init-from" mode with its own record, not a loosened
    check.

D.13 [POST-AUDIT] Validate caches in a shared function; bind caches to
     their producer (Fix 2)
  Decision: one validator called at the top of the shared forward(), plus
    an ApplicationCache list subclass carrying the producing model (weak
    reference) and schedule.
  Alternatives: (a) a dedicated cache class replacing the list: cleaner,
    but changes the return type every caller and test uses; (b) per-slot
    checks inside attention: errors would surface mid-forward, after
    earlier slots had run; (c) no provenance, shapes only: cannot catch
    cycle-vs-sequence caches, which have identical shapes.
  Pros: the control's code path changes by four lines; valid caches are
    unaffected (bit-exact re-check); every malformed case found fails
    with the slot named.  Cons: one Python loop over A slots per cached
    forward (GPU latency impact unmeasured); plain lists have no
    provenance.
  Validating experiment: 17 malformed-cache cases plus provenance tests;
    mutation M2 fails 24 tests.
  Abandon if: measured decode-latency overhead becomes material at large
    A.  Then validate once per generate() call instead of once per step.

D.14 [POST-AUDIT] Measure, do not change, the prefill K/V storage retention
     (Fix 3)
  Decision: report exact logical and retained-storage KV bytes.  Do not
    make prefill K/V contiguous copies.
  Alternatives: copy K/V out of the fused QKV buffer at prefill (frees Q
    sooner, costs a copy); preallocate a static cache (removes the
    concatenation transient but is a bigger change to the control's
    inference path).
  Reason: either alternative changes the CONTROL's memory profile.  The
    remediation brief forbids modifying the primary architecture beyond
    the required fixes, and the effect is identical for both arms.
  Abandon (make the change, to both families) if: measured peak inference
    memory at the target context shows the transient or retained storage
    is a material share of the 4 GiB budget.  Decide it as an explicit,
    versioned change to the baseline.


==============================================================================
PART E - LIMITATIONS AND OPEN QUESTIONS
==============================================================================

Not done / not known:
  E.1  NO training, NO evaluation, NO GPU profiling was performed.  Nothing
       is known about capability, perplexity, throughput on the reference
       GPU or real peak VRAM of any recurrent configuration.  (Post-audit:
       still true.  An RTX 5080 is present, but the project environment has
       no CUDA build of torch, and none was installed.)
  E.2  Increased inference latency: decode compute per token is proportional
       to A.  A 2-block model at depth 8 runs 16 block applications per
       token, the same as a 16-layer model.  Sharing does not make anything
       faster.  Repeated weights may get slightly better cache locality on a
       GPU, but that is unmeasured.
  E.3  KV-cache overhead: proportional to A, not N (C.9).  At 8K context it
       dominates memory for every planned arm.  This is the most likely
       reason for the hypothesis to fail.
  E.4  Optimisation instability: shared tensors receive r summed gradient
       contributions (C.6).  The baseline's LR (6e-4), clipping (1.0) and
       warmup were tuned for unshared layers.  Stability was only checked
       at initialisation (depth 8, fp32 and bf16 autocast on CPU).
  E.5  Reduced independent capacity: a shared block must serve all its
       positions, with no iteration-specific parameters (D.3).
  E.6  Failure of iterations to add capability: possible.  Diminishing
       returns with depth are likely; how strong they are is unknown (ablation
       C).
  E.7  Scaling: all planned arms are about 7-65M parameters.  Conclusions
       may not transfer to the sizes relevant for the 4 GiB target.  In
       particular the weights/KV balance changes with width (C.9).
  E.8  Context: both models use learned absolute positions sized to
       context_length (512 in baseline_small).  8K usable context is not
       supported by either model yet.  The positional scheme must be decided
       for both arms before 8K experiments.
  E.9  Dataset: tinyshakespeare (about 0.3M train tokens) cannot support
       capability conclusions.  At 3000 x 8192 tokens every arm sees it
       about 80 times, and arms with fewer parameters may win through
       regularisation alone.  A larger corpus needs authorisation.
  E.10 Single seed in all configs: at least 3 seeds per arm are needed to
       separate effects from noise.  [POST-AUDIT] The planner can now emit
       per-seed configs (--seeds); the pilot plan uses 3 paired seeds.
  E.11 Environment: tests ran on Python 3.13.17 + torch 2.15.0+cpu.
       DML-0001 used torch 2.11.0+cu128 on CUDA.  GPU kernels (flash/
       mem-efficient SDPA) were not exercised by these tests.
  E.12 No git: the folder came from a ZIP without .git, so
       collect_env_info() cannot record a commit hash for new runs, as
       RESEARCH.md requires.  The repository should be cloned or initialised
       with git before any authorised run.
  E.13 DML-0001's local checkpoints are not on this machine.  Their
       loadability is argued from unchanged parameter names and the
       backward-compatible config, but was not tested.
  E.14 Known inconsistencies inherited from the previous generation and NOT
       resolved here: RESEARCH.md and ROADMAP.md define M1 differently;
       DML-0001 metadata says status RUNNING although the run was stopped
       (an operator decision); README refers to a results/ directory that
       does not exist.
  E.15 [POST-AUDIT] Remaining correctness risks after the fixes (details
       in POST_AUDIT_FIXES.txt, "Remaining limitations" of each fix):
       - Profiling fixes (CUDA sync, peak over runs, device-wide snapshot)
         are NOT verified on CUDA.  The project environment is CPU-only.
       - [Re-review + round 3: resolved] Resume compares tokenizer hashes
         and the hashes and real token counts of the packed .bin files.  A
         lock taken in Trainer() covers loading, recovery, the CLI's
         metadata and status writes, and training.  Remaining: older
         checkpoints lack some or all provenance fields (resume warns); a
         hard-killed process leaves a stale lock; the lock is a
         cooperative file lock; there is no explicit fork mode.
       - [Round 4] Only the non-finite stop condition of the pilot plan is
         implemented; divergence, sustained grad-norm, memory and time
         stops are not.  Under fp16, long runs of scaler-skipped steps are
         not flagged.  Report code must use read_metrics(), not the raw
         metric files.  The no-repeat sampler and full-split evaluator do
         not exist yet.
       - Cache provenance exists only on caches returned by forward().
         Cache CONTENT is never validated (stale weights, hand-built lists).
       - Prefill K/V retain the fused QKV buffer (1.5x logical bytes); the
         decode concatenation keeps old and new caches alive together.
         Both are measured, not changed (D.14).
       - Pickle-based resume state (trusted artifacts only), metadata
         races, multiple-choice tokenisation boundaries and sampled
         validation windows (Codex DML-A05/A06/A07) are unchanged.
       - Very large legal recurrence depths are not capped.

Open questions:
  - Does per-iteration early-exit loss keep decreasing with iteration count?
  - Is cycle better than sequence?  Does a single block (R01x8) collapse?
  - Would iteration-aware relaxations (per-iteration norms or LoRA) recover
    most of the unshared quality while keeping storage small?
  - Can KV sharing across recursions be trained without large losses, which
    would remove the main memory penalty?

  tensor counts) and confirmed on disk for a toy model (checkpoint size
  independent of depth).  Inference-memory savings are THEORETICAL and
  partly negative: the KV cache grows with effective depth, and at 8K
  context it outweighs the weight savings for all planned sizes.  No GPU
  memory was measured.

Are additional experiments needed?
  Yes: the full controlled matrix (Experiments A, B, C), on a larger corpus,
  with at least 3 seeds per arm, real CUDA profiling at the target context,
  and pre-registered thresholds.  All of this requires authorisation.
  [POST-AUDIT] The first step is the three-arm pilot in
  docs/DOMOVOI_PILOT_PLAN.md (B02 / R02x4 / B08, 3 paired seeds, 100M tokens
  each, about 1.5e17 training FLOPs estimated), after its prerequisites.

The architecture has been implemented, but no meaningful capability improvement has yet been demonstrated.
